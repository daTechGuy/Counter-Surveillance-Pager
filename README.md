# Counter-Surveillance-Pager

*(Renamed from Flock-Sky-Spy once scope grew past just Flock cameras + drones. If you're looking at a repo still named flock-sky-spy, this is the same project, later in its history.)*

## What this is

Combines six detectors into one Pager payload:

- **Flock Safety detection**, two independent paths sharing one dedup/alert pipeline:
  - **BLE name scan** -- taken verbatim from Flock-You / Flock_Detect. Unmodified scan loop, unmodified alert logic.
  - **WiFi wildcard-probe + IE signature** -- a port of flock-you's current (and, per its own commit history, more reliable) WiFi detection method, with a refreshed 40-entry OUI list (see Credit above). See `flock_wifi_monitor.awk`.
- **Mesh-Detect surveillance watchlist**, two independent paths, config-driven via `mesh_detect_targets.conf`:
  - **BLE**: OUI prefix / full MAC / device-name substring match against `hcitool lescan` results (reuses the Flock BLE scan's own output rather than running a second scan).
  - **WiFi**: OUI prefix / full MAC match against the transmitter of any 802.11 management frame. See `mesh_wifi_monitor.awk`.
  - **Ships with ~50 real, vendor-labeled OUI entries active by default** -- police body/dash cameras, ALPR/surveillance camera companies, and professional CCTV manufacturers -- plus another ~20 consumer/SMB camera-vendor entries commented out by default (higher false-positive risk since those vendors also sell ordinary consumer routers/APs). See `mesh_detect_targets.conf`'s header for the full breakdown and sourcing.
- **Rogue BLE tracker detection** (`rogue_tracker_monitor.awk`) -- structurally matches Apple Find My, Tile, Samsung SmartTag, and Google Find My Device Network beacons, which are *engineered* to defeat OUI/MAC watchlists via rotating addresses, so this matches the advertisement payload structure instead of the MAC. A single sighting proves nothing (could be anyone's tracker in a store); the actual signal is **persistence** -- the same identity staying near the Pager for a sustained window (15+ min, 3+ sightings by default) -- except for Google's FMDN protocol, which self-flags "unwanted tracking protection activated" via a dedicated frame-type byte and gets an immediate alert instead of waiting on the persistence window. See `payload.sh`'s `handle_tracker_line()` and `tracker_allowlist.conf` (for suppressing your own trackers).
- **Drone Remote ID detection** -- a from-scratch Linux port of what Sky-Spy does on ESP32, reimplementing its detection logic directly against the ASTM F3411 / Open Drone ID spec for the Pager's own BLE and WiFi radios, using `hcidump` and `iw`/`tcpdump` instead of ESP-IDF.
- **Deauth-flood detection** (`deauth_eviltwin_monitor.awk`) -- counts Deauthentication/Disassociation management frames per transmitter MAC. A single deauth is normal WiFi churn (a client actually disconnecting); a rapid burst from one source is the signature of an active attack (aireplay-ng, mdk4, ESP32 "deauther" boards). Works standalone, no config needed. Rate decision (not just raw count) lives in `payload.sh`'s `handle_deauth_line()`, using a delta-based calculation (count/time since the *last* hit line, not since the start of the run) specifically so a slow trickle of normal disconnects over hours doesn't eventually cross a naive cumulative threshold.
- **Evil-twin AP detection** (same file, same process) -- flags a Beacon advertising a trusted SSID name from a BSSID not in your configured allowlist, i.e. someone broadcasting your home/work WiFi's name to get your devices to auto-connect to them instead. Config-driven via `trusted_networks.conf`, which ships **empty** -- only you know your own network's real SSID/BSSID(s).

All four WiFi detectors (Flock probe + Mesh-Detect + drone Remote ID + deauth/evil-twin) share one radio hopping channels 11/6/1 (250ms dwell) instead of drone detection's old fixed channel 6 -- see Known limitations. The rogue tracker detector shares the BLE radio with the drone BLE detector and the Flock BLE scan the same way (its own passive `hcidump` reader, piggybacking on whatever scan window is already open) -- no new radio time for this either.

**On "detect everything without overloading the Pager":** the Mesh-Detect watchlist expansion is deliberately a *data-only* change -- more OUI/MAC/name entries in a text file, matched by string/hash comparisons that were already running. It adds zero new capture processes, zero new radio time, and zero new BLE/WiFi scan windows. Broader coverage came from enriching the target list an existing, already-running matcher checks against, not from adding more things listening to the radios.

## Why this needed real engineering, not a copy-paste

Sky-Spy's own README describes what it detects (WiFi Beacon + WiFi NAN + BLE broadcasts of drone position/ID), but the actual bytes-on-the-wire format isn't in that repo -- it's implicit in the ESP-IDF/Arduino build. Getting it right required going to the reference implementation and spec:

- [`opendroneid-core-c`](https://github.com/opendroneid/opendroneid-core-c) -- `libopendroneid/opendroneid.h` (encoded message struct layouts), `opendroneid.c` (scale factors: `LATLON_MULT=1e7`, `ALT_DIV=0.5`/`ALT_ADDER=1000`, `SPEED_DIV`), `odid_wifi.h`/`.c` (vendor IE / NAN OUIs and frame structure)
- [`transmitter-linux`](https://github.com/opendroneid/transmitter-linux/blob/main/bluetooth.c) -- exact BLE legacy advertising byte layout (Service Data, UUID `0xFFFA`, AD App Code `0x0D`)

All of this is cited inline in `rid_common.awk`.

### Why awk, not python3

The first version of this was written in python3. It turned out this Pager (`mipsel_24kc` / `ramips` target, 24.10.1, `no-all busybox` build, ~30MB overlay flash) has **no python3 available at all** -- confirmed live against the actual device: `which python3` finds nothing, and `opkg list` shows no python3 package in the configured feeds for this target, not just "not installed." Chasing a hand-built static python3 for this exact old MIPS chip was judged not worth the uncertainty, so the decoders were rewritten from scratch in POSIX-ish awk, run via BusyBox's own `awk` (confirmed present, along with the specific functions needed: `index`, `substr`, `toupper`, `sprintf`, `fflush`).

### What was actually verified, and how

Every layer of this was checked against **real captures pulled from this specific device** during development, not just generic docs, because two format assumptions turned out to matter a lot:

1. **`hcidump --raw`'s exact text format** (direction marker, hex-byte wrapping) -- confirmed by fetching bluez-hcidump's own `parser.c`/`hcidump.c` source, then cross-checked against a real ~6-second BLE capture from this device. One of the real advertising reports in that capture was hand-decoded byte-by-byte (MAC, AD structures, RSSI) to confirm the LE Advertising Report event's "structure of arrays" layout (all event types, then all address types, then all addresses, then all lengths, then the concatenated data blocks, then all RSSIs -- not one struct per report).
2. **`tcpdump -xx`'s hex-dump layout** -- confirmed against a real 3-beacon capture from this device's `wlan1mon`. The radiotap `it_len` field read from the real bytes (56) landed exactly on `frame_control = 0x0080` (Beacon) when used to compute where the 802.11 frame starts, and offset `dot11_start + 10` landed exactly on the real source MAC -- both hand-verified against the actual hex, not assumed.
3. **The awk decoders themselves** -- round-trip tested locally (via `gawk`, functionally equivalent to the device's `awk` for everything used here) against: (a) the real, unmodified BLE and WiFi captures from this device, to confirm zero false positives and no crashes on ordinary ambient traffic; and (b) synthetic Basic ID / Location / System messages injected into correctly-framed copies of those same real captures (single BLE legacy advertisement, a 3-message WiFi Beacon pack, and a 3-message WiFi NAN Service Descriptor attribute), to confirm detection actually fires and every field decodes to the exact input value. The full FIFO-based pipeline wiring in `payload.sh` (capture tool -> named pipe -> awk) was also tested end-to-end locally to rule out any deadlock in the producer/consumer startup ordering.

None of this required guessing at busybox-awk-specific behavior blind -- every primitive it depends on was confirmed running on the real device first (see the conversation this was built in).

## Requirements per detector (each degrades independently)

- **Flock BLE** (unchanged from Flock-You): `hciconfig`, `hcitool` -- if these were on your Pager before, nothing changes here.
- **Flock WiFi**: + `awk`, `iw`, `tcpdump`, and a usable second radio (`phy1`/`wlan1mon`) -- same prerequisite as Drone WiFi below, and shares that radio/channel-hop with it.
- **Mesh-Detect BLE**: none beyond Flock BLE above (reuses its `hcitool lescan` output). Active by default -- `mesh_detect_targets.conf` ships pre-populated (see Credit above); becomes a no-op only if you empty the file out.
- **Mesh-Detect WiFi**: same as Flock WiFi (`awk`, `iw`, `tcpdump`, `phy1`/`wlan1mon`). Active by default for the same reason.
- **Rogue tracker BLE**: `awk`, `hcidump` (own reader, alongside Drone BLE's). Active by default, no config needed -- `tracker_allowlist.conf` only matters once you want to suppress your own tracker's alerts.
- **Deauth flood**: same as Flock WiFi (`awk`, `iw`, `tcpdump`, `phy1`/`wlan1mon`). Active by default, no config needed.
- **Evil-twin AP**: same detector/process as deauth flood. No-op until `trusted_networks.conf` has a `trusted:` entry.
- **Drone BLE**: + `awk`, `hcidump`. Both confirmed present on this device.
- **Drone WiFi**: + `awk`, `iw`, `tcpdump`, and a usable second radio (`phy1`/`wlan1mon`). See Known Limitations below for the radio-contention fix this needed.

## Known limitations (by design, not oversights)

- **The WiFi radio is `phy1`/`wlan1mon`, and needs one persistent device config change to actually work reliably.** Found by driving past an actual Flock camera and getting no hit: `phy1`/`wlan1mon` is the Pager's own default-configured primary recon interface (`/etc/config/pineapd`: `hop '1'`, `bands '2,5'`, `hopspeed 'fast'`, auto-started at boot), which was actively fighting this payload's own channel-hop loop for the same interface -- `wifi_hop.log` filled with continuous `Resource busy (-16)`, and the interface's actual channel was observed drifting onto 5GHz (44, 144), nowhere near the 2.4GHz 11/6/1 this payload's detectors need. `phy0`/`wlan0mon` was tried as an alternative and ruled out -- confirmed live that channel-set on it fails 100% of the time, even completely idle, because `phy0` also hosts `hostapd`/`wpa_supplicant`-managed interfaces that lock the phy's channel. The actual fix is a scoped `uci` config change on the device itself (not carried in this repo): `uci set pineapd.wlan1mon.hop='0' && uci commit pineapd && /etc/init.d/pineapd restart`. This stops `pineapd` from channel-hopping `wlan1mon` without disabling it or touching its recon logging on any other interface. **A fresh Pager needs this applied manually** -- see `payload.sh`'s header for the full writeup and verification notes. **Residual risk**: if the Pager's native AP/hotspot ever gets used on `phy1` while this payload runs, or if something else re-enables the `hop` option, the same contention could return.
- **Drone BLE detection is not continuous.** It piggybacks on Flock-You's own `hcitool lescan` windows (~12 of every ~15 seconds) rather than running a separate scan, so it inherits that duty cycle. Continuous BLE scanning independent of the Flock cycle would need its own `hcitool lescan`/`bluetoothctl` session, which risks fighting the Flock scan for the single BLE radio -- left as a follow-up if the merged duty cycle proves insufficient in practice.
- **All four WiFi detectors now hop channels 11/6/1** (250ms dwell, matching flock-you's own hop set/order/timing) instead of drone detection's old fixed channel 6. A drone, camera, or Mesh-Detect target transmitting only on 5GHz, or on a 2.4GHz channel outside 11/6/1, will still be missed.
- **Deauth-flood rate thresholds (`DEAUTH_FLOOD_RATE=3`, `DEAUTH_FLOOD_MIN_DELTA=5`) are reasoned defaults, not calibrated against a real attack tool's actual frame rate.** The rate math itself is delta-based (count/time since the *last* hit line, not cumulative since the run started) specifically so a slow trickle of normal disconnects over hours can't eventually cross a naive cumulative threshold -- verified with standalone scenarios (real flood, normal single disconnect, slow trickle, cooldown suppression). Unit-tested, not field-confirmed against a real deauth attack.
- **Evil-twin detection only checks Beacon frames, not Probe Response** (which also carries SSID+BSSID) -- a rogue AP that only replies to probes and never beacons would be missed. `trusted_networks.conf` ships **empty**; no vendor list applies the way it did for Mesh-Detect, since only you know your own network's SSID/BSSID(s).
- **`flock_wifi_monitor.awk`'s detection logic is unit-tested, not field-confirmed.** Its tcpdump/radiotap framing reuses the byte offsets already hardware-verified for `rid_wifi_monitor.awk`, and its OUI/wildcard/IE-signature logic has been checked against synthetic packets built to exactly match flock-you's own published fingerprint constant -- but not yet against a real camera's actual RF. If a real camera's IE signature has drifted from that constant (which is plausible -- flock-you's own commit history shows the fingerprint approach superseding an earlier OUI-only method, implying the on-air signature isn't fixed forever), this will miss it the same way the unmodified BLE path apparently already can.
- **8 of the 40 Flock OUI entries (04:0d:84, f0:82:c0, 1c:34:f1, 38:5b:44, 94:34:69, b4:e3:f9, b4:1e:52, d4:11:d6) are "candidate" tier**, not independently confirmed by nite-oui-collection's curated tracker at the time they were added here -- see `flock_wifi_monitor.awk`'s header for exactly which entries these are and why they were still included (same evidentiary bar as several pre-existing entries already in flock-you's own list). If any turn out to be false positives, expect them to eventually get pulled the same way `f8:a2:d6`, `94:2a:6f`, and `f4:e2:c6` already were.
- **Mesh-Detect's default watchlist will produce more false positives than the tightly-gated Flock WiFi detector, by design.** It's OUI/MAC matching on any management frame or BLE advertisement, not a behaviorally-verified signature -- a hit means "a device from a listed manufacturer is nearby," not "this specific device is confirmed surveilling you." The Tier-1 entries (police/LE/ALPR/dedicated-CCTV vendors) are lower-risk since those vendors don't also sell generic consumer routers; the Tier-2 entries (commented out by default -- Ubiquiti, TP-Link, D-Link, Wyze, etc.) are higher-risk for exactly that reason. See `mesh_detect_targets.conf`'s header before uncommenting Tier 2.
- **`mesh_wifi_monitor.awk`'s logic is unit-tested only** (synthetic packets + a synthetic config file, off-device with `gawk`), same "ported, not field-confirmed" caveat as `flock_wifi_monitor.awk`.
- **Rogue tracker detection has no GPS and cannot tell "this tracker followed me across locations" from "this tracker sat near wherever the Pager is for 15+ minutes."** It's the same class of heuristic Apple/Android's own on-device unknown-tracker alerts use, minus their location-diversity refinement. A tracker in a stationary neighbor's apartment/car could false-positive if you stay put nearby; a tracker on a fast-moving vehicle you're not in could false-negative if it's only briefly in range. Google's FMDN protocol is the exception -- its `0x41` "unwanted tracking" frame type is the device self-reporting, so that one alerts immediately, no persistence window needed.
- **Rogue tracker allowlisting needs periodic maintenance** for the three rotating-MAC protocols (Apple/Samsung/Google) -- there's no "add once, forget forever" option without deriving your own tag's actual rotating key from your account credentials, which is out of scope. Tile's MAC doesn't rotate, so a Tile allowlist entry is permanent. See `tracker_allowlist.conf`'s header.
- **`rogue_tracker_monitor.awk` only checks each protocol's header** (AD type + company/service ID + type byte), not deeper payload fields (Apple's status-byte bits, Samsung's battery/aging-counter fields, FMDN's hashed-flags byte) -- confidence in those exact sub-byte semantics from the sources consulted wasn't as solid as the header-level signatures, and the header alone is enough to identify the protocol. `rogue_tracker_monitor.awk`'s logic is unit-tested only (synthetic packets for all four protocols + two negative cases + the emit-throttle, with `gawk`), same "ported, not field-confirmed" caveat as the WiFi detectors -- not yet checked against a real AirTag/Tile/SmartTag/FMDN accessory.
- **BLE Extended/Long-Range advertising (Bluetooth 5) is not decoded** -- only Legacy advertising (the common case for consumer drones). Same gap applies to rogue tracker detection: a tracker using only BT5 extended advertising (not confirmed either way for any of the four protocols) would be invisible to `hcidump`'s legacy-advertising capture.
- **Auth messages are identified but not decoded** (their content isn't useful for a recon alert).
- UI alerts are cooldown-throttled per MAC (10s for drone Remote ID, 5min for rogue trackers -- `ALERT_COOLDOWN` / `TRACKER_ALERT_COOLDOWN` in `payload.sh`), and deduplicated once per session per MAC for both Flock paths and both Mesh-Detect paths, since repeat detections of the same device would otherwise spam the console. The loot logs are **never** throttled -- every decoded message/hit is recorded, including every rogue-tracker sighting that hasn't yet crossed the persistence threshold.

## Confirmed live on hardware

Beyond the local decoder testing described above, on the actual Pager:

- The `hcidump`/`awk` (BLE) and `tcpdump`/`awk` (WiFi) background pipelines -- all 5 of them concurrently (2x `hcidump`, 3x `tcpdump`) -- start, stay running, and produce **zero stderr output**, confirmed via `ps` and the pipelines' own log files while `payload.sh` was live.
- A synthetic hit line appended directly to the WiFi hits file while the payload was running was picked up on the very next drain cycle and produced a correct on-screen `DRONE REMOTE ID` alert (title, MAC, decoded UAS ID, and transport all correct) -- confirming the full chain end to end: capture -> awk decode -> bash hit parsing -> cooldown/dedup -> `LOG`/`LED`/`RINGTONE`/`ALERT_RINGTONE`.
- **Mesh-Detect WiFi is field-confirmed with a real detection**: caught an actual nearby Axis Communications camera (OUI `50:c7:bf`) during normal operation, correctly labeled and logged.
- **Rogue tracker BLE is field-confirmed with real detections**: caught multiple real Apple Find My "offline finding" beacons during normal operation (structural match, correctly logged at `sighting=1`, correctly held below the persistence threshold rather than falsely alerting on a single sighting). The persistence-*alert* path itself (15+ min sustained) hasn't been triggered by a real tracker yet, only by synthetic/backdated test scenarios.
- **The `phy1`/`wlan1mon` radio-contention fix is field-confirmed**: after `uci set pineapd.wlan1mon.hop='0'`, channel-set succeeds 100% of the time (was 0% intermittently, then observed as continuous failures during a real ~50-minute run), and the channel was confirmed cycling cleanly through 11/6/1 for a full 10-second poll under full 3x-`tcpdump` capture load, with only 1 transient `Resource busy` over the whole test.
- The fixed `trap cleanup EXIT; trap 'cleanup; exit 130' INT; trap 'cleanup; exit 143' TERM` (see Known Limitations) is field-confirmed: SIGTERM now cleanly kills every child process and removes every FIFO, verified via `ps` showing zero remaining processes after the signal.
- Flock Safety **BLE** detection is the original, untouched Flock-You code path, so it carries the same confidence as upstream, but has not yet produced a real hit on this device (see What's genuinely still unverified).
- Flock Safety **WiFi**, Mesh-Detect BLE, rogue tracker structural matching for the other 3 protocols, and deauth/evil-twin have all been checked with `gawk` against synthetic packets (see each detector's own section above) -- unit-tested logic, not all of it field-confirmed yet.

## What's genuinely still unverified

- **Flock detection specifically has not yet produced a confirmed real hit.** One real-world test (driving past a known camera) produced no hit, but was later found to be caused by the `phy1`/`wlan1mon` radio-contention bug (now fixed, see Known Limitations) rather than necessarily a detection-logic problem -- the real test hasn't been repeated since the fix. That's the natural next step: watch for `wifi_flock|` lines in `flock_wifi_hits.log`, or a BLE name-match, the next time you're near a known camera.
- Real-world timing and coverage against an actual Remote-ID-broadcasting drone -- wasn't available during development, still untested.
- Deauth-flood and evil-twin detection, entirely: brand new, unit-tested against synthetic packets and standalone bash scenarios only (see Known Limitations), never run on-device or against a real deauth tool / real rogue AP. Watch `deauth_eviltwin_hits.log` and the loot file for the first real test -- and remember `trusted_networks.conf` needs your own network's SSID/BSSID(s) added before evil-twin detection does anything at all.
- Rogue tracker **persistence alerting** specifically (as opposed to the structural match, which is now field-confirmed): whether a real tracker sustained near the Pager for 15+ minutes actually crosses the threshold and fires the loud alert hasn't been observed yet, only simulated with a backdated timestamp.

Loot: `/root/loot/counter_surveillance_pager/surveillance_<ts>.txt` (Flock + Mesh-Detect hits, same line format as upstream flock-you), `/root/loot/counter_surveillance_pager/drone_rid_<ts>.txt` (every decoded drone message: time, transport, MAC, message type, fields), `/root/loot/counter_surveillance_pager/rogue_trackers_<ts>.txt` (every tracker sighting, including ones still below the persistence threshold), and `/root/loot/counter_surveillance_pager/deauth_eviltwin_<ts>.txt` (every deauth/disassoc frame count and every evil-twin sighting, including ones below the alert cooldown).
